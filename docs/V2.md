## V2-1 — Recurrence detection v2

The likeliest remaining source of error. MVP uses a median-gap heuristic in a
25–35 day window.

Possible refinements, each measured against the calibration table:

- Non-monthly cadences: weekly, fortnightly, quarterly. Widen the accepted
  gap bands and record how many new streams appear.
- Amount drift: a stream whose amount trends upward (rent increases, index-
  linked bills). Use the most recent occurrences rather than the whole-series
  median.
- Termination detection: a stream with no occurrence for more than two
  cadences before `request_date` has probably ended. Currently it keeps being
  predicted forever.
- Confidence scoring per stream, so low-confidence streams can be flagged in
  the explanation or handled by rule 4.

Revert anything that does not move the calibration deltas.

## V2-2 — Sensitivity analysis

For each sample row, perturb the ledger by ±1% and record whether the chosen
plan changes. Rows where a tiny change flips the recommendation are the rows
where the answer is genuinely borderline.

Two payoffs: it tells you where remaining accuracy is winnable versus where
it is coin-flip, and it is a strong interview answer to "how confident are you
in these outputs?"

## V2-3 — Second-opinion adjudication

For rows the ranker finds near-tied — two plans within a small margin on sort
key 3 — surface the tie in a diagnostics file rather than resolving it
differently.

If you do add a model to adjudicate, it must select **between two already-safe
plans the deterministic core produced**. It may never generate a plan, alter
an amount, or override a safety verdict. Any such adjudication is logged with
both candidates and the reason.

Measure it. If it does not beat the pure sort on the samples, cut it and say
so in the README — a negative result you can defend is worth more than a
feature you cannot.

## V2-4 — Explanation fidelity

If `decision_explanation` is similarity-scored rather than exact-matched,
squeeze the templates: compare word-for-word against all 25 samples, check
number formatting at the edges (trailing zeros, single-digit dates, four-digit
amounts), and confirm the date format for every month name.

Cheap, zero risk, and it touches all 250 rows.

## V2-5 — Extended test coverage

Property tests rather than examples:

- `amount_safe_to_pay` never exceeds `requested_amount`, for any generated
  ledger
- adding an outflow never increases `amount_safe_to_pay`
- `earliest_date_for_full_payment` is monotone: raising the requested amount
  never moves the date earlier
- the sort key is a total order over any candidate set

These catch classes of bug that the 25 samples cannot.

## V2-6 — Interview preparation

Not code, and possibly the highest value per minute remaining.

Write `docs/defence.md` with a crisp answer to each:

- Why deterministic core rather than an LLM per request?
- How do you know the outputs are right, given hidden ground truth?
- What does the ablation table show, and what surprised you in it?
- Where does the system fail, and how would you know?
- What did you try that did not work?
- How is prompt injection handled, and why is that the right approach when the
  shipped data contains none?
- Why is `decision_explanation` templated rather than generated?

The last two are the ones a sharp judge will reach for. Have the calibration
table and the ablation table open during the call.
