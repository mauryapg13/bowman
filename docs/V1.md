## V1-2 — Vision port (`code/ports/vision.py`)

16 blank amounts, each with exactly one linked image, each image file present.
No blank amount lacks an image, so the rule-4 fallback is not needed here.

Input: `image_id` **and the linked event's `description`**. The description is
what disambiguates the field to read. Called from `amounts.py`, never from
`load.py`.

Expected effect, from recon: 12 of the 16 are settled one-offs dated 1–3 days
before the request — already inside the balance, so they change nothing but a
category median. The 4 pending/scheduled ones (`event_1442`, `event_1786`,
`event_6033`, `event_6859`) settle inside the window and do move the curve.
If any of the 12 shifts a calibration delta materially, the ledger is wrong,
not the extractor.

Output schema:

```json
{"amount_raw": "1,00,000.00", "amount": 100000.0, "currency": "INR",
 "field_used": "Balance Due", "confidence": 0.0}
```

Known traps, all confirmed by recon:

- `image_01` — payslip with gross, subtotal, deductions and Net Pay. The
  linked event is a net salary credit; read **Net Pay**.
- `image_02` — rent receipt with Total, Amount Received and Balance Due. The
  linked event is an outstanding balance; read **Balance Due**. Indian lakh
  grouping (`2,00,000.00`) and the right edge is cropped.
- `image_11` — hospital bill whose itemised lines sum to 3150 while the
  printed total says 3650. **The printed total wins.** Never recompute.
- `image_16` — invoice screenshot with a stray UI button in frame.
- `event_7307` — a **USD** blank amount for an INR user. Extraction *and* FX
  conversion, using `2025-10-01,USD,INR,83.33`.
- Eight images were not opened during recon. Inspect them before trusting the
  extractor.

Two backends behind one signature per spec §8 P8. Cache every result.

**Verify against the calibration table**: these 16 users should show a
reduced delta after this task. If one gets worse, the wrong field was read.

## V1-3 — Message operations (`code/ports/ops.py`)

215 messages: 39 event-linked, 176 not. The 176 are not noise — they carry
salary increases, income endings, temporary reduced pay, new jobs, rent
increases and date changes. Roughly 45 are Indonesian; send them as-is.

Closed enum: `cancel | amend_amount | delay | confirm | amend_stream | none`.

Targets come from an allow-list: existing `event_id`s for that user, plus that
user's detected stream identifiers. Anything else collapses to `none`.

`amend_stream` carries `{stream_id, new_amount?, effective_date?, ended?}` —
enough to express a raise from a date, an ended income, a temporary
reduction, and a rent increase, and nothing more.

Ordering: apply message operations **after** recurrence detection and
**before** the ledger, so an amendment changes the stream that prediction then
extends.

Two specifics from recon: `message_86` mixes an image reference with a
confirmed future salary in a single message — one message may need to yield
more than one operation. And several messages set a *future* effective date,
so the stream carries an old amount before it and a new one after.

**Expected effect: the largest of any V1 task.** 228 users have no scheduled
salary row, and these messages are the only confirmed forward income signal
many of them have.

## V1-6 — Iterate

Run the scorer. Read every mismatch by hand. The order to work in:

1. Calibration deltas first. A wrong ledger makes every other column wrong,
   and the delta tells you the size and sign of the error.
2. `affordability_status` and `recommended_payment_method` next — categorical
   and likely exact-match scored.
3. `decision_explanation` template fidelity last. Cheap points, zero risk.

Log each hypothesis, change and score delta in `docs/v1_log.md`. Revert
anything that does not help.

## V1-7 — Deliverables

### `code/evaluation/usage_report.md`

Must describe the run that produced the submitted `output.csv`. Instrument
token counting from the first port call — do not reconstruct it at the end.
Include providers, model names, call counts, input and output tokens, totals
and per-request averages, estimated total and per-request cost, and per-model
breakdowns if more than one model is used.

Expect a small number: 16 vision calls plus roughly 215 message calls, both
cached, and zero explanation calls because that column is templated. Say so
explicitly — low token usage with high accuracy is a result, not an omission.
